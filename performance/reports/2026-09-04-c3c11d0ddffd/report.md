# 双实例跨实例业务链路：本机 Docker 性能基线

## 结论摘要

本报告只描述 commit `c3c11d0ddffdffcb29378e836b7d7e05a360c3c0` 在一台开发机上的 Docker 运行结果，不代表生产容量、并发用户数、SLA 或 SLO。

- 在双实例直连、目标 `5 transaction/s` 的确认档中，连续完成 **3 次 × 5 分钟**运行，共完成 **4502 笔完整业务事务**。
- 三次运行的完整业务链路成功率和清理成功率均为 **100%**；合计 **0 次跨实例状态不一致、0 个 HTTP 5xx、0 个 dropped iteration**，也没有非预期 409 或 HTTP 429。
- 三次业务链路 P95 分别为 `3384.00 ms`、`94.00 ms`、`97.05 ms`。第一轮存在明显延迟离群，因此本轮**不设置也不宣称任何 P95 门槛**；三次 P95 的中位数只能作为描述性统计，不能当作 SLA。
- 目标 `12 transaction/s` 的探索档未通过：实际完成 `11.471 transaction/s`，出现 `172` 个 HTTP 5xx 和 `20` 个 dropped iteration。运行时日志将 172 个 5xx 全部对应到 app-1 的全局 `room:create` 锁等待超时；详见 [failure-root-cause.txt](failure-root-cause.txt)。
- `1`、`2`、`4`、`6`、`8 transaction/s` 各只有一次 3 分钟探索结果。它们可用于定位本机基线，但样本时长和重复次数不足，不能据此宣称“最大容量”或“稳定支持 X 并发”。

## 被测环境与链路

压测器 k6 与被测容器共享同一台 Windows 开发机。k6 通过宿主机端口分别直连 app-1 `http://localhost:18081` 和 app-2 `http://localhost:18082`，绕过 Nginx；两个应用实例共享 MySQL 和 Redis。

一次事务覆盖 12 个核心业务请求：双端游客登录、app-1 建房、app-2 跨实例读房并加入、双方跨实例选角与准备、房主查询并开始游戏、app-2 校验开局状态。事务结束后再读取最新版本并由房主退出、解散房间。所有写命令携带幂等键，需要并发控制的命令携带上一响应的 `stateVersion`。

本轮测试不覆盖公网、TLS、CDN、跨主机网络、Kubernetes、大量 WebSocket 长连接、断线重连或消息风暴。游客登录不包含注册写库和密码哈希；开局步骤会读取 MySQL 中的角色及卡牌目录。完整环境记录见 [environment.txt](environment.txt)。

## 测试方法

1. 启动独立 Compose 项目，预热 JVM、连接池、MySQL 与 Redis 路径。
2. 对双实例直连链路按 `1 / 2 / 4 / 6 / 8 / 12 transaction/s` 分档探索，每档目标时长 3 分钟；每个 transaction 通常对应 14 个 HTTP 请求（12 个核心业务请求加 2 个清理请求）。
3. 选择 `5 transaction/s` 做三次重复确认，每次 5 分钟。本轮为了快速建立可复现基线，未执行原计划的 30 分钟长稳测试。
4. 正确性门禁检查完整链路、单步骤、清理、跨实例一致性、非预期冲突、限流响应、服务端错误和 dropped iteration；延迟门禁未启用。
5. 同时以约 5 秒间隔保存 `docker stats`。原始资源采样位于 [resources/docker-stats.ndjson](resources/docker-stats.ndjson)。

等效复现命令见 [commands.txt](commands.txt)。本目录没有保存 k6 的逐点 `metrics.ndjson`，因此本报告以各阶段 `summary.json`/`summary.md` 和 Docker 资源采样为审计依据。

## 12 transaction/s 失败与资源观察

12 档的 app-1 负责所有建房请求。资源采样在该阶段记录到 app-1 CPU 峰值 `106.57%`，内存最高 `767.9 MiB / 768 MiB`。这说明当时资源压力较高，但资源相关性不能替代错误日志；本轮已直接定位的失败路径是全局建房锁等待超时。

`RoomService` 使用固定键 `xiyouji:lock:room:create` 串行化所有房间创建，并最多等待 5 秒。超时后 `RedisDistributedLockService` 抛出 `IllegalStateException`，通用异常处理器把它映射为 HTTP 500。固定到达率继续注入事务，等待锁的请求累积，随后出现业务失败和 dropped iteration。完整证据、限制和修复建议见 [failure-root-cause.txt](failure-root-cause.txt)。

## 数据清理与证据限制

- 三次确认运行的 `business_cleanup_success` 都为 100%。这表示房主退出后逻辑房间已解散；幂等记录仍按约 10 分钟 TTL 自然过期。
- 如果建房已提交但响应在返回房间码前丢失，脚本无法定向清理该房间，只能依赖房间 TTL。本轮摘要不能证明不存在这种未识别残留。
- Redis 使用 AOF；逻辑删除和 TTL 到期不表示数据卷文件立即缩小。
- Nginx 低速 E2E 运行在本轮中断，`nginx/` 没有可用摘要，所以本报告不声称已完成 Nginx 端到端性能验证。
- 本目录没有保留容器镜像 digest、完整容器日志或 k6 逐点指标；这些是下一轮报告应补齐的审计材料。根因日志计数来自运行时检查，已在根因文件中明确标注这一限制。
