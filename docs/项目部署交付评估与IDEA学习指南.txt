一、目前项目处于什么阶段

结论：项目已有完整业务骨架、本地运行方式和部署工程基础，适合作为学习项目和演示项目。距离公网展示，主要差固定发布版本、当前版本回归和真实服务器验收；距离长期对外运营，还差数据恢复、故障处理、容量与运维闭环。

本次结论来自当前工作区源码、配置、CI 文件及仓库内验收报告的静态检查。本次没有重新执行构建、测试、压测，也没有连接真实服务器或核验远端 CI。因此，下文“已有”表示存在实现或历史证据，不表示当前版本已经通过上线验收。

特别注意：git status 显示当前有多处未提交修改，包括战斗奖励、多人房间、WebSocket 同步、地图推进，以及新增测试和 CardRewardSampler。README 中的“79 个 Maven 测试、9 个前端单测、4 个浏览器测试”等属于历史记录，不能直接当作这一批修改的验收结果。

项目实际架构是“五模块模块化单体”，双实例是同一个 Spring Boot 应用运行两份，共享 MySQL 和 Redis。它采用 DDD 分层思想及 Port/Adapter，但领域层仍有 JPA/Jackson 注解，应用层仍依赖 Spring 等框架。

二、离部署和交付还差什么

【第一优先级：交付任何固定版本前完成】

1. 收敛当前修改并形成可复现版本。
   审查未提交及未跟踪文件，确认哪些属于交付范围，再提交和打版本标签。源码提交、测试结果、镜像和交付文档应对应同一版本。不能让本机包含新增 Java 类，而交付仓库或构建环境中缺失它。

2. 对当前版本重新执行完整回归。
   前端：Vitest、TypeScript 检查、生产构建、Playwright。
   后端：Maven verify、ArchUnit、JaCoCo 门禁、MySQL/Redis Testcontainers。
   部署：Compose 构建与健康检查、双实例 REST/STOMP 黑盒 E2E。
   业务重点：注册登录、游客恢复、完整单人战斗与奖励、多人选角准备、五人上限、断线重连、重复提交、奖励未确认时禁止推进、所有玩家完成奖励后返回地图。
   通过标准：保留同一提交的结果及失败处理记录，不只验证首页能打开。

3. 补齐交付物。
   至少包括版本号、源码提交号、固定镜像标识、环境变量说明、部署命令、验收步骤、已知限制、升级和回退步骤、数据备份恢复说明。
   仓库已有 README、部署指南和脚本，可以在这些基础上整理，不必重写所有文档。
   根目录未发现 LICENSE；公开分发前还需明确项目许可证以及插画、字体等素材的来源与使用许可。

【第二优先级：公网展示前完成】

4. 在真实目标服务器部署并验收 HTTPS/WSS。
   已有 docker-compose-cloud.yml、scripts/deploy-cloud.sh、docs/vps-deployment.md，以及发布镜像工作流。
   尚缺仓库能够证明的公网部署验收：实际服务器、域名、证书、反向代理、外网访问、跨浏览器多人同步及服务重启后的行为。
   按当前文档先使用单实例 VPS 展示方案即可；该方案更新时允许短暂停机。

5. 落实生产配置及访问边界。
   注入独立随机数据库密码和 JWT 密钥，使用 prod 配置和真实 CORS 域名，避免使用 standalone 的开发密钥。
   云端 Compose 默认把应用绑定到 127.0.0.1，这是已有基础；仍需验证服务器的实际端口和代理规则。
   SecurityConfig 仍允许匿名访问 Swagger/OpenAPI、实例信息以及部分监控接口。必须核验公网代理确实限制内部接口；不能仅凭启用 prod 就认为这些入口已隐藏。
   cloud Compose 当前使用 MySQL root 连接。正式交付应改为专用业务账户，并明确数据库迁移需要的权限。

6. 将发布与验证结果绑定。
   release-image.yml 已能构建并推送 GHCR 镜像，但流程本身没有自动等待同一提交的 CI 通过。
   发布前必须核对相同提交的绿色 CI；后续可以增加自动发布门禁。交付时记录镜像 digest，避免仅凭可被重新打标的标签定位产物。

【第三优先级：长期运行或有稳定性承诺时完成】

7. 数据备份与恢复演练。
   MySQL/Redis 已挂载数据卷，Redis 已启用 AOF，但持久化不能替代异机备份。
   本次未发现完整的备份恢复脚本和恢复验收记录。需要确定备份频率、保存位置、保留时间、可接受的数据损失量与恢复时间，并实际演练。
   Redis 保存权威游戏状态；RedisSessionStore 的会话 TTL 为 24 小时，保存时设置 TTL。需明确这是临时会话还是长期存档，不能把用户账户保存在 MySQL 等同于游戏进度永久保存。

8. 故障一致性与升级兼容性。
   房间、战斗、幂等结果和通知存在分别写入的路径。锁可以串行化并发，但不能自动保证进程在多个写入之间崩溃时的原子性。
   应验证状态已保存但幂等结果未完成、事件未发出、Redis 重启、应用重启等场景，必要时补充恢复机制。
   升级还要验证旧 Redis JSON 能否被新代码读取、Flyway 迁移后旧镜像能否运行。回退镜像不等于回退数据库。

9. 容量和监控闭环。
   历史压测记录：本机双实例环境以 5 笔业务事务/秒运行三轮，每轮五分钟，共 4502 笔，业务成功率 100%。该场景主要验证建房、加入、准备、开局，并不代表持续战斗或公网容量。
   目标 12 笔事务/秒时历史报告出现 172 个 HTTP 5xx，定位到全局建房锁超时。当前 RoomService 仍使用 xiyouji:lock:room:create 和 5 秒等待，因此瓶颈尚不能视为已修复。
   可将房间码生成改为原子占位并处理冲突重试，保留房间粒度锁，再重新压测；不要直接删除锁。
   小规模展示可先设定限流与容量边界；有并发承诺时需覆盖真实代理、持续战斗、长连接、断线风暴及长时间运行。
   完整 Compose 有监控基础，精简 cloud Compose 没有完整监控栈。正式运行需接通告警接收、日志保留、磁盘和 Redis 内存监控。Redis 当前采用 noeviction，内存满时写入可能失败。

10. 不把可选架构改造作为上线前置条件。
    K8s 清单目前是离线 schema 校验过的草案，真实集群、Ingress、滚动升级、扩缩容和恢复仍需验收；只有选择 K8s 交付时才成为必需项。
    拆分大 Service、净化领域层有维护价值，但不是小规模演示上线的必要条件。当前优先完成版本、回归、真实部署和恢复说明。

三、用 IDEA 打开后，先怎样运行

1. 打开项目根目录或根 pom.xml，按 Maven 项目导入五个模块。
2. Project SDK 和 Maven 使用 JDK 17。项目有 Maven Wrapper，优先使用仓库提供的版本。
3. 找到 xiyouji-bootstrap 模块中的 com.xiyouji.XiyoujiApplication。
4. 创建 Java/Spring Boot 运行配置，classpath 选 bootstrap，程序参数填写：
   --spring.profiles.active=standalone
5. standalone 使用 H2、内存 Store 和本地锁，无须 MySQL/Redis；适合单步调试规则。重启会丢失内存数据，也不能用于学习跨实例一致性。
6. 在 IDEA 终端中进入项目根目录，执行：
   npm ci --prefix frontend-vue
   npm run dev --prefix frontend-vue
   后端使用 8080，前端 Vite 使用 5173，配置已代理 API 和 WebSocket 到后端。
   浏览器打开 http://localhost:5173，通过页面触发后端断点。
7. 前端 build 输出在 frontend-vue/dist；不要把“前端构建成功”等同于“IDEA 启动的后端已装配最新页面”。学习时使用 Vite，完整打包部署时按 Dockerfile 的资源装配流程验证。
8. 学完业务后，再切换 MySQL/Redis 环境，比较 InMemory/Local 与 Redis/Redisson 两组实现。

四、优先学习哪些核心框架

第一层：Java 17、Spring Boot、Spring MVC 和依赖注入。
理解启动扫描、构造器注入、Controller 参数校验、DTO、异常到 HTTP 响应的映射，以及不同 profile 如何选择配置和实现。
入口：XiyoujiApplication、GameController、BattleController、RoomController、GlobalExceptionHandler。

第二层：模块分层、Port/Adapter、Spring Data JPA 和 Flyway。
理解 Controller 调用用例服务，服务通过 Port 获取数据，基础设施提供 JPA/Redis 实现。
MySQL 主要保存账户和游戏目录数据，Redis 保存运行中的状态，两者职责不同。
入口：application/port 下的接口、infrastructure/repository 下的 JPA 接口、DataInitializer、db/migration 下 V1～V4 SQL、ArchitectureTest。

第三层：Spring Security、JWT 和 BCrypt。
理解登录签发令牌、HTTP 请求识别身份、WebSocket 认证，以及资源所属用户和房间成员权限检查。认证通过并不自动获得任意房间操作权限。
入口：AuthService、JwtUtil、JwtAuthenticationFilter、SecurityConfig、WebSocketAuthInterceptor。

第四层：Redis、Redisson、STOMP 和状态一致性。
这是项目最值得深入学习的工程部分：共享状态、房间粒度锁、状态版本、幂等响应重放、跨实例通知、断线对账。
入口：CommandGuard、CommandIdempotencyService、RedisIdempotencyStore、RedisDistributedLockService、RedisRoomEventPublisher/Subscriber。

第五层：Vue 3、TypeScript、Pinia 和组合式函数。
理解页面负责交互、Store 管理客户端状态、API 封装命令、WebSocket 触发刷新及重连。
入口：frontend-vue/src/stores/game.ts、stores/room.ts、api/retryCommand.ts、composables/useStomp.ts。
Three.js 主要用于视觉展示，可放在主业务和同步机制之后学习。

第六层：测试和部署工具。
结合 JUnit/Mockito、ArchUnit、Testcontainers、Vitest、Playwright 理解不同层次的验证范围，再看 Docker Compose、Nginx 和 CI 如何把它们串起来。

五、优先学习哪些核心算法

1. 分层有向无环图的随机地图生成。
   MapService.generateLayer：按行生成节点，中间行随机生成 2～4 个节点；按列距离选择下一行的相邻节点连接，再给无来源节点补连接。
   边始终指向下一行，因此形成 DAG；从唯一首行节点逐行保证来源连接，可以推导各行节点可从起点到达。
   补连接后某个节点的出边可能超过最初选择的 1～2 条，要以实现为准。
   重点学习：节点和边的数据结构、概率阈值、可达性、不变量、moveToNode 的合法移动约束。这里没有必要先学最短路径算法。

2. 抽牌、洗牌、弃牌和消耗牌的状态流转。
   GameCharacter.initBattle、drawCards、playCard、endTurn。
   观察 deck、drawPile、hand、discardPile、exhaustPile 的关系，以及抽牌堆不足时的处理。
   重点检查：不会凭空复制或丢失卡牌、能量不足不能出牌、消耗牌不会普通回收、战斗副本不会污染目录模板。

3. 回合状态机与伤害结算。
   BattleService 的 startBattle、playCardAndResolve、endTurnAndResolve，以及 GameCharacter/Enemy 的 takeDamage、tickBuffs。
   跟踪“玩家操作—敌方行动—胜负判断—奖励待确认—返回地图”的合法顺序。
   重点是力量、格挡、伤害和 Buff 的结算次序及边界，而不是只看一条伤害公式。

4. 敌人意图的规则调度。
   Enemy.chooseIntent 使用 patternIndex % movePattern.size() 循环选择行动，再用 switch 映射攻击、防御、增益等行为。
   这是预设行动序列与规则逻辑；没有行动模式时使用默认攻击。适合学习取模循环、策略表达和可预测敌人行为。

5. 按稀有度加权、优先不重复的奖励采样。
   CardRewardSampler.draw：先按角色过滤并按名称去重，再将剩余卡牌按稀有度分组；按 COMMON/UNCOMMON/RARE/LEGENDARY 的 50/30/10/10 权重选组，再在组内等概率选牌。
   抽中过的牌从本轮候选中移除；候选耗尽后才允许下一轮重复。
   注意：权重属于“稀有度组”，不是每张卡；某组为空后剩余组重新归一化，所以最终每张牌概率并非固定 50/30/10/10。
   该类是当前未跟踪的新文件，交付前应纳入版本管理并运行对应测试。

6. 分布式命令的一致性控制。
   CommandGuard.fingerprint 用 SHA-256 计算 method/path/body 指纹，Redis SET NX 抢占幂等键，已完成命令可以重放响应；CommandGuard.checkVersion 拒绝旧状态写入。
   Redisson 锁解决并发串行化，版本号解决旧客户端修改，幂等键解决同一业务意图重复提交，三者职责不同。
   它属于并发控制协议，不是共识算法；短期幂等也不等同于任意故障下的“恰好执行一次”。

7. 客户端事件去重与权威状态对账。
   stores/room.ts 根据 eventId 和状态版本处理事件，当前实现还带有周期对账；useStomp.ts 处理重连及重建订阅。
   重点思考：事件重复、旧事件晚到、漏事件、HTTP 响应乱序、退出房间后旧请求返回时如何避免覆盖新状态。

六、核心代码阅读顺序和断点建议

以下是 IDEA 中的类名或定位后缀，可用 Search Everywhere 搜索。完整文件位置由项目根目录加模块与源码目录确定。

第一条主线：单人新游戏。
frontend-vue/src/stores/game.ts → GameController → GameService → MapService.generateLayer → SessionStore。
配合 GameSession 和 GameCharacter 看会话、角色、地图如何装配。先使用 InMemorySessionStore，之后读 RedisSessionStore。

第二条主线：一张卡牌完成结算。
BattleController → BattleService.playCardAndResolve → GameCharacter.playCard → Enemy.takeDamage → 战斗结束与奖励处理。
断点观察 handIndex、energy、hp、block、stateVersion 和 cardRewards；分别触发正常出牌、能量不足、击杀、重复领奖。

第三条主线：多人房间开局。
RoomController → RoomService 的建房、加入、选角、准备、startGame → RoomStore → RoomEventPublisher。
观察 RoomStatus、成员数量、角色唯一性、房主权限和版本递增。用两个浏览器窗口观察同一命令如何影响两端。

第四条主线：多人战斗和奖励屏障。
MultiplayerBattleController → MultiplayerBattleService.playCard/endTurn → resolveReward → returnToMap。
配合 MultiplayerBattleState、RoomPlayer 和 MultiplayerPlayer，观察共享敌人状态、每名玩家回合状态、奖励确认以及返回地图条件。

第五条主线：一次写命令如何防重放。
StrictCommandHeadersFilter → Controller 的幂等处理 → CommandIdempotencyService/CommandGuard → 业务锁与版本校验 → Store 保存 → 响应缓存及通知。
不同接口的包装顺序有所差异，要沿选定的实际接口调用链阅读，不要假设所有接口实现完全一致。

第六条主线：跨实例同步。
RedisRoomEventPublisher → Redis Pub/Sub → RedisRoomEventSubscriber → STOMP → useStomp.ts → stores/room.ts → REST 对账。
学习为什么共享状态放 Redis，而 WebSocket 通知不承担唯一状态来源。

测试阅读顺序：
GameCharacterTest、EnemyTest、BattleServiceTest：理解业务规则。
CardRewardSamplerTest、MapRewardGuardTest：理解奖励及推进边界。
RoomConcurrencyTest、CommandGuardTest、DistributedStateTest：理解并发和重试。
DistributedInfrastructureContainersTest、DistributedComposeE2ETest：理解真实中间件及跨实例验证。
roomSync.test.ts、useStomp.test.ts、reward-confirmation.spec.ts、room-resilience.spec.ts：理解前端同步与异常路径，其中部分是当前新增文件。

七、建议的学习成果

第一阶段：能在 IDEA 启动 standalone，并从页面操作跟进到 Java 断点。
第二阶段：能解释地图如何保证连通、一张牌如何结算、奖励为何必须确认。
第三阶段：能解释房间锁、版本号、幂等键分别防什么问题，说明它们的故障边界。
第四阶段：能用两实例解释共享状态、跨实例通知与 REST 对账。
第五阶段：能用固定版本在另一台机器复现，并交出测试记录、部署说明和恢复步骤。
